# WoW: Forever — Gameplay Optimization

Working notes and validated data for optimizing every class in **World of Warcraft: Forever**
(Blizzard's Classic+ release, launching **November 4, 2026**). The project is organized **by class**; each class has player pages for
two modes, `leveling/` (solo, fight lab) and `raid/` (full raid), and the research behind them under `research/`. This page explains how
the project works; the player index is the top-level [`README.md`](../README.md). Rules for working in the repo: [`CLAUDE.md`](../CLAUDE.md);
state of the work and open items: [`HANDOFF.md`](../HANDOFF.md); the current work list: [`page-audit.md`](page-audit.md).

## Working assumption

WoW: Forever uses the Classic talent system (9 classes, 3 trees each, **51 points**, 7 tiers, gold-medal
talents at 11/21/31 points plus a **new 1-point talent at the 16-point mark**), but the trees themselves
are **revamped** (build 70291: 140 new talents, 105 Classic talents removed, 244 changed). So:

1. **Classic Era optimal builds are the baseline** — they encode which talents matter for each spec.
2. **The Forever trees are read from the beta client** (the build `_reference/data/data_build.py` names: 1.60.1.70291, refreshed
   2026-10-08: 466 talents with tiers, every rank's tooltip, prerequisites and a diff against Classic; earlier pulls and the BlizzCon
   demo snapshot are archived under `data/raw/`).
3. **Each Classic build is audited** talent-by-talent against the Forever tree and re-spent into a **hand draft**; the stats model,
   the fight lab, the community raid simulator and the healer lab then race the drafts against the builds their searches find
   (🔬 derived builds), and the player pages show the winners ([`methodology.md`](methodology.md)).
4. Everything Forever-specific is a hypothesis until it is checked in the live game: simulator and lab numbers are models.

rewrites the talent-tree pages, the Fight lab / Raid sim / Healer lab README sections and summaries, guide.md, gear.md and consumables.md
(needs a simulator checkout), rotation.md, every build page and Research files section, the new-builds survey, the player pages and top
README, the tier list, respec plans, optimizer sections, scorer changes, the loop audit, both checklists, the fight-lab summary and the
report index. It does **not** rewrite (each has its own tool): the spells READMEs (`build_forever_spells.py --render-only`),
`forever-talents/README.md` (`refresh_forever_talents.py`), `dps-rankings.md`, the "DPS by gear tier" sections and `gear-links.json`
(`raidsim/ml_builds.py --rank`), the raid-sim, fight-lab, healer-lab, deep-optimization and open-search reports (the searches and races
that write them), the optimizer pages, the PvP check and the audits; the page numbers come from those records, so run their tools first
when the records are stale (audit 2026-10-18 row 80). A
build's research folder comes from its `content` field (leveling and solo -> `research/leveling/`, raid and dungeon -> `research/raid/`,
pvp -> `research/pvp/`); its spec (the player page it appears on) from `spec_modes.py`: a tank or healer build belongs to its role's tree,
otherwise the tree with 30+ points, otherwise a hybrid of its two biggest trees; a build's `spec` field overrides this (Frostfire,
Shockadin, Smite, the 31/0/20 Frostbolt mage). Raid pages rank on full-raid DPS (user decision 2026-10-02), leveling pages on fight-lab
time per kill; each spec plays its own rotation (user rule 2026-10-08). Build fields: [`_templates/build-schema.md`](../_templates/build-schema.md); class page template: [`_templates/class-README.md`](../_templates/class-README.md).
Planned per-class addition: `professions/`.

## Tooling (`_reference/data/`)

All build docs are **generated from JSON** so the numbers can never drift from the text. Every script runs from any directory and
takes optional class names (`... warrior druid`); each has its usage in its docstring.

```
python _reference/data/validate_builds.py && python _reference/data/render_builds.py   # check every build, regenerate build pages + indexes
python _reference/data/rebuild.py --steps regen                                        # regenerate the pages (what it covers: above)
python _reference/data/rebuild.py [classes] --jobs 3                                   # the whole pipeline (hours): calibrate <-> optimize, race, report, regen
python _reference/data/check_beta_build.py                                             # is there a newer beta client? prints the refresh command
python _reference/data/refresh_forever_talents.py --fetch --raw <date>-beta-<build>    # pull and merge a new beta build (then CLAUDE.md's steps)
python _reference/data/raidsim/setup.py                                                # build the community raid simulator (once per machine)
python _reference/data/deep_class.py <class>                                           # a class's deep searches and everything after them
bash _reference/data/run_open_searches.sh [classes]                                    # the open talent searches (pause and resume at will)
python _reference/data/linkcheck.py                                                    # every relative markdown link that points at nothing
```

## Stats model (scorer)

Hand-drafted builds are the *starting* answer; the **scorer** (`_reference/data/scorer/`) parses every tooltip into numbers, values
hand-entered procs with their arithmetic written down, scores each talent for a spec model and use-case (leveling single-target, AoE
grinding, solo at 60, raid DPS, parse, raid healing, raid tanking, PvP), finds the best legal 51-point build and orders it level by level.
It reproduces the known-optimal Classic builds (calibration table in `scorer/README.md`) and is calibrated to the fight lab, the raid
simulator and the healer lab; its Forever results are exported as `opt-*` builds next to the hand drafts and summarised in the
"Optimizer" section of each research README. `scorer/changes/<class>.md` lists every talent's Classic->Forever buff/nerf verdict;
`<class>/research/leveling/respec-plan.md` says whether a mid-leveling respec pays for itself.

## Fight lab (Monte Carlo fight simulator)

The scorer is an expected-value model; the **fight lab** (`_reference/data/fightlab/`) plays leveling fights out in time with dice for
every class (same-level mobs from the Classic 1.12 creature database, including caster mobs; beta-client ability numbers; gear from the
Classic item database) and measures time per kill, deaths, downtime and the value of each talent. It calibrates the scorer's leveling
values, races the builds, runs the open leveling search, and writes `<class>/research/leveling/fightlab/`, the "Fight lab" section of
each research leveling README and [`fightlab-summary.md`](fightlab-summary.md). The leveling pages rank on it. Every number is a
simulation of stated assumptions, not a beta measurement.

## Raid sim (community simulator) and healer lab

For level 60 the community's simulator (the ElliotWood/Forever wowsims fork, pinned in `raidsim/setup.py`) models the beta's spells,
items, buffs and rotations, with this project's patches. `_reference/data/raidsim/run.py` races every raid build next to the simulator's
own preset talents, on a training dummy (the races and calibrations) and in a full raid (what the raid pages rank on), and writes
`<class>/research/raid/raidsim/`, the "Raid sim" section of each research raid README and [`raidsim-summary.md`](raidsim-summary.md).
[`dps-rankings.md`](dps-rankings.md) ranks every damage spec in pre-BiS and phase-1 BiS gear. Healers are in no community simulator:
the **healer lab** (`heallab/`) measures their capacity ([`heallab-summary.md`](heallab-summary.md)); tanks are scored on tank value in
the simulator. Simulations of the community's model and ours, not measurements.

## Editing rules (short version)

- Edit `builds.json` / `proposed-builds.json`, never the generated `.md` pages; then run validate + render.
- Talent names must match the datasets exactly (the validator will tell you).
- Anything about Forever must say which beta build it is based on; beta numbers change between builds.
- Keep the class folders identical in shape — a new optimization category gets the same sub-folder name in every class.

See [`CLAUDE.md`](../CLAUDE.md) for the full conventions and [`methodology.md`](methodology.md) for how builds are derived.
